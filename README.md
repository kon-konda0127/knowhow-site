# アラフォーから始める趣味（ダンス・ダイエット・AI開発 ノウハウサイト）

Instagram・YouTube・X から収集したノウハウを論点ごとに整理する個人学習サイト。

## フォルダ構成

```
knowhow-site/
├── inbox/            ← スクショ・テキストを放り込む場所
│   ├── dance/
│   ├── diet/
│   └── ai/
├── notes/            ← 構造化済みMarkdownノート（Claudeが生成）
│   ├── dance/
│   ├── diet/
│   └── ai/
├── assets/           ← SVG図解・装飾画像・プロンプト集
（inbox/・notes/ の各カテゴリフォルダは、そのカテゴリを実際に使い始める時に作る）
└── docs/             ← 公開するHP（HTML/CSS/JS）
    ├── index.html    ← トップページ
    ├── dance.html    ← ダンス一覧
    ├── diet.html     ← ダイエット一覧（旧 running.html は転送ページとして残置）
    ├── ai.html       ← AI開発一覧
    ├── style.css     ← 共通スタイル
    ├── notes-dance.js   ← ダンスノートデータ
    ├── notes-diet.js ← ダイエットノートデータ
    ├── notes-ai.js      ← AI開発ノートデータ
    └── notes/        ← 各ノートのHTMLページ
```

※ `inbox/` はGitに含めない（個人素材のため）。処理済みスクショはノート生成後に**削除**する。

## ノート品質基準（inbox処理時に適用）

対象読者：AI活用者・技術中級者（専門用語の過剰解説は不要。実践的な情報密度を重視）

### 全カテゴリ共通
- **冒頭に「なぜこれが重要か」を1〜2文で書く**（背景・文脈）
- 出典は「@アカウント名 のポスト（X）」または「動画タイトル（YouTube/Instagram）」形式で正確に記載
- 推測・不確かな情報は「※要確認」と明示
- 「#X投稿用」タグは社長が指示した時だけ付ける

### ライティング基準（2026-08-13追加。コラム以外の全ノートに適用）
コラムで実証済みの品質（論文式＋チャンキング）を、短いノートにも比率を落として適用する。根拠にした上級者の技法は3つ。

1. **結論先行**（Google テクニカルライティングの原則）: 冒頭の「なぜ重要か」は背景説明ではなく、**「これを読むと何が変わるか」を最初の1文**にする。1文1アイデア、長い複文は割る
2. **説明と手順を混ぜない**（Diátaxis: 技術文書の標準分類）: 「しくみ・なぜ効くか」（説明）と「やり方」（手順）を別セクションに分離する。箇条書きの羅列に説明を紛れ込ませない
3. **事実と自分の文脈を分離**（コラム第1号の論文式）: SNSからの取り込み情報（伝聞）と、自分の環境での意味付け（**「うちの体制ではこう使う」**）を別セクションにする。**体験の捏造は禁止**。実際に試していないものは「未検証」と書き、試した記録（日報・ミス台帳）があるものだけ体験として書く

追加ルール:
- SNS由来のインストール手順・コマンドは**「※SNS情報・未検証」を見出し脇に明示**し、導入前にリポジトリURL・作者・ライセンスの裏取りを促す1文を添える（Obsidianスキル導入の教訓）
- ノートの3点セット（notes/*.md 正本・notes-*.js・docs/notes/*.html）は必ず同時に更新し、内容を一致させる
- **段落と箇条書きは短く割る**（2026-08-13社長指摘）: 1段落は2文まで（3文以上になったら段落を分ける）。箇条書き1項目は原則1〜2文。長い1項目は複数項目に分割する
- **目次はモバイルで本文より先に表示**（style.cssの `.toc-sidebar { order:-1 }` で対応済み。ノートページの雛形を変える時はこの挙動を壊さない）

### AI開発ノートのセクション構成（2026-08-13 ライティング基準に合わせて改訂）
- **なぜ重要か**（結論先行。「これを読むと何が変わるか」を最初の1文に）
- **しくみ（なぜ効くか）**（説明。手順を混ぜない）
- **うちの体制ではこう使う**（自分の文脈での意味付け。実際の記録があるものだけ）
- **インストール/実行方法**（番号付きステップ。SNS由来なら見出し脇に「※SNS情報・未検証」）
- **よくあるミス・落とし穴**
- **出典**

冒頭には **要点箱（`tldr-box`「⏱ 30秒でわかるこのノート」4項目）** を必ず置き、`reading-time` は「要点30秒・全文◯分」形式で書く（読者の負担を先に示す。2026-08-14適用）。

### 気になったX投稿の取り込み（2026-08-14 運用開始）

AI開発ノートは、Xで見つけた気になる投稿の置き場も兼ねる。取り込み元は本体リポジトリ側のXスカウト台帳（`~/Documents/claude/docs/x_scout_log.md`）。指示は「**Xスカウト台帳から転記して**」。

1. 台帳のエントリは、**採用も見送りも全件転記する**（見送りを記事にすることの意味は次項）
2. 台帳の「ステータス」列にある採否判断（採用／見送りとその理由）を、そのまま「うちの体制ではこう使う」に書く。**見送りの理由こそ価値がある**ので省略しない
3. 投稿本文は転記しない。**自分の言葉の要約＋パーマリンク**のみ（台帳の運用ルールと同じ。著作物の転載を避けるため）
4. 台帳に無い詳細を補わない。推測は「筆者の考察」、未確認は「※要確認」と明示する
5. 転記したら台帳のステータス末尾に「ノウハウサイトAI開発へ転記済み（YYYY-MM-DD・ノートID）」を追記する（二重転記の防止）

### 採否ラベル（2026-08-14 社長指示で導入）

**見送りにしたものこそ記事にする。**理由は2つ。読んだ人が「自分にも必要か／自分には要らないか」を判断できること、そして「何を採らなかったか」が検証した証拠になること。

- 全ノートに `verdict`（`採用` / `見送り` / `未判定`）と `verdictReason` を付ける（`docs/notes-ai.js`）。`docs/category.js` が一覧カードにバッジと理由を出す
- **タイトルの先頭に `【採用】`『【見送り】』`【未判定】` を付ける**。一覧をタイトルだけ眺めても要否が分かる状態にする
- 見送りの理由は分類まで書く: **重複**（すでに社内にある。何と重複したかまで書く）／**環境不一致**／**原則と衝突**
- ノート冒頭には採否パネル（`verdict-panel`）を置き、「判定・理由・逆に必要かも（またはその案件で取り込んだ結果）」を3行で示す
- `未判定` は、この運用より前に取り込んだノート等、社長の判断がまだのもの。**推測で採用/見送りを埋めない**
- 中身が短報（ニュース等）の場合、セクションは「なぜ重要か／何があったか／うちの体制ではこう使う／よくあるミス／出典」でよい。手順が無い投稿に手順節を作らない。見出し名は内容に合わせて言い換えてよい（例「インストール方法」→「試すなら」「実践のしかた」）

### ダンスノートのセクション構成
- **なぜ重要か**（この動きが上達に効く理由）
- **ポイント**
- **よくあるミス**
- **練習ドリル**（回数・時間の具体値）
- **ステップ図解**（`assets/dance-steps/`に画像があれば表示。無ければ省略）
- **出典**

## ステップ図解画像のルール（ダンス基本ステップ）

- 保存先: `docs/assets/dance-steps/`（**必ずdocs/配下に置くこと**。GitHub PagesはリポジトリのDocs/フォルダのみを公開しており、`docs/`の外に置いた画像は本番で404になる。`inbox/`のスクショとは別で、こちらは完成した図解を恒久的に置く場所）
- 命名: 英語のステップ名・小文字・ハイフン区切り（例: `two-step.png`）。日本語ファイル名は使わない
- 画像内にテキスト・ラベルを入れない（AI生成の日本語文字は崩れるため。ラベルはHTML側で表示する）
- 生成プロンプトの型: `assets/image-prompts-dance-basic-steps.md` を参照
- ノートデータ（`notes-dance.js`の`DANCE_NOTES`）に`images: ["ファイル名.png"]`を追加すると、一覧カードのサムネイルと詳細ページの図解に自動反映される

### ダイエットノートのセクション構成
扱う範囲は4つ。1つのノートで全部を埋める必要はなく、**そのノートで扱うものだけ**書く（空の項目は画面に出ない）。

- **なぜ重要か**（続けやすさ・健康・リバウンド防止への影響）
- **運動**（`training`）— 有酸素・筋トレ・ストレッチなど体を動かす話
- **食事**（`meal`）— 食べ方・栄養バランス・自炊アプリとの連携
- **記録**（`record`）— 計測方法、数値の読み方、停滞期の捉え方
- **習慣**（`habit`）— 続ける仕組み、モチベーション、挫折からの復帰
- **メモ・注意点**（`notes`）
- **出典**

> 体重・体脂肪率などの**実測値は個人情報**。公開サイトに載せるのは「何をどう測ったか」の方法論に留め、実数値を書く場合は社長の明示的な指示を得ること。
> 効果には個人差があるため、断定を避けて「〜という方法がある」「自分の場合はこうだった」と書く（コラムの事実／考察の分離と同じ流儀）。

## コラムカテゴリの運用（正式仕様: メインリポジトリ docs/spec_ai_column_system.md）

- コラム＝実体験（日報・ミス台帳・Obsidianメモ）を一次資料に、**事実と考察を分離**して書く読み物。構成テンプレートは仕様書4章（リード→背景→事実→分析→考察→限界→まとめ）
- 事実セクションは出典（日報の日付等）必須。考察セクションは「〜と考えられる」等の限定表現を使う
- **「ネタ出しして」**と指示されたら: `docs/daily_report.md`・直近のObsidianデイリーノート・`docs/mistake_log.md`・公開ネタ帳.md（いずれもメインリポジトリ/Vault側）を横断して読み、コラム候補を**3〜5件・出典付きでチャット上に提示**する。自動でファイルに書き込まない。社長が選んだものだけ公開ネタ帳.mdへ追記する（追記前に日付＋ネタ文言の重複チェック）
- 下書きは `notes/column/YYYYMMDD_スラッグ.md`（frontmatterの`status: draft`）。**社長の承認前はコミット・pushしない**（このリポジトリはpublicのため）
- 公開前チェック（必須）: 個人情報（収入・成績）・認証情報・非公開リポジトリURL・卒論未発表内容が含まれていないか確認し、社長の明示的な「公開して」を待つ。自作アプリの実名は書かず一般名に抽象化する（2026-08-12社長決定）
- 公開したら `notes-column.js`・`docs/notes/column/` に反映し、公開ネタ帳.mdの該当行を「公開済み」に更新する

### コラムの可読性基準（ADHD・認知特性への配慮。2026-08-13制定）
長文の壁は読み飛ばし・離脱を招くという研究知見（W3C「Making Content Usable」COGA設計ガイドのチャンキング/平易な言葉、ADHD読者の読書行動研究）に基づき、全コラムで以下を適用する:
1. **冒頭に「⏱ 30秒でわかるこの記事」ボックス**（3項目以内）。流し読みだけで結論が取れる入口を必ず作る
2. **本文の段落は1〜2文まで**。3文以上になったら分割か箇条書き化
3. **詳細・出典は折りたたみ（`<details>`）へ**（段階的開示）。見出し行1行＋開けば全文、の2層にする
4. **数字は文章に埋めず可視化**: 単発の数字→統計タイル、時系列→タイムライン、分類・比較→表（表は`.table-wrap`で横スクロールをコンテナ内に収める）
5. 太字は「その行の主張」だけに使う（scanning読みで太字だけ拾えば要旨が通る状態にする）
6. 読了時間は「流し読み◯分・全文◯分」の2段表記
- 専用CSS部品: style.css末尾の「コラム可読性部品」ブロック（tldr-box / stat-row / timeline / claim-list / check-list / table-wrap）
- 本文を改稿したらfrontmatterの`version`を上げ、`changelog`に理由を1行残す
