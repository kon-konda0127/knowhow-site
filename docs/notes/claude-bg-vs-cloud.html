# なぜ重要か

これを読むと、SNSで見た「便利な裏技」を、試す前に公式の定義と突き合わせる手順が持てる。

機能が実在することと、紹介された説明どおりに動くことは別になる。実在の確認だけで納得すると、名前の似た別機能を掴んだまま運用に組み込んでしまう。

# 何が紹介されていたか

  • プロンプトの先頭に記号を1つ付けると、タスクがWeb側へ渡り、バックグラウンドで実行されるという紹介
  • 手元のコマンドライン側を司令塔、Web側を実働部隊として使い分ける構想が述べられていた
  • ※上記は投稿の要約。この説明のどこが実際と違ったかを次の項に書く

# 確かめたこと（事実）

確かめ方は2段階にした。まず公式ドキュメントで定義を読み、次に機微なデータを含まない空のフォルダで1回だけ動かす。空のフォルダに限定したのは、外に何が出るか分からない段階で、本番のデータを置いたフォルダを使わないため。

公式のコマンドリファレンスを読むと、関係する機能は3つに分かれていた。どれも起動時に付ける指定（フラグ）である。

  • バックグラウンド化のフラグ（--bg）: 手元の端末でバックグラウンドエージェントとして起動し、専用の管理コマンドで扱う。Webへの送信は伴わない
  • Webセッションを作るフラグ（--cloud）: こちらがWeb側に新しいセッションを作る機能
  • 行き来のためのフラグ（--teleport）: Web側のセッションを手元の端末で再開する機能

投稿の説明は、このうち --bg と --cloud を一つの動きとして語っていた。公式のヘルプ記事でも、「セッションをバックグラウンド化すること」と「ローカルとWebを切り替えること」は並べて書かれているだけで、同じ動作としては説明されていない。

実際に動かして確認もした。手順は次のとおり。

  1. 機微な情報を含まない空のフォルダを用意する
  2. そこで claude --bg を1回だけ実行する（当時のバージョンは 2.1.228）
  3. 一覧コマンドで、種別が「background」、作業フォルダが手元のパスであることを確認する
  4. 確認後は claude stop で片付ける

結果として、実行は手元で完結し、外部への送信は発生しなかった。

# うちの体制ではこう使う

2026-08-15、この投稿は見送りと判断した。理由は2つある。

1つ目は、同じことがすでにできること。長い作業を非同期で走らせる仕組みはチームの規程に組み込み済みで、監査やテストを担当するサブエージェントはバックグラウンドで起動し、目安の時間の2倍を過ぎたら一度だけ様子を聞き、それでも返事がなければ打ち切って範囲を絞り直す。この形だと結果を整った状態で受け取れる。

今回の方法は、ログが画面の描画データをそのまま返すため、結果を機械的に読み取れなかった。

2つ目は、投稿が言う「Webへ渡る」動きが別のフラグの話だったこと。Web側で動かすかどうかは、扱うデータの機微さに直結する判断になる。混同したまま運用へ入れるわけにはいかない。

# 検証の副産物（いちばん役に立った発見）

確認のために動いているセッションの一覧を出したところ、承認待ちのまま止まっていたセッションが2件見つかった。起動してからの経過は 24.0時間と 23.5時間（承認待ちになった時刻そのものは記録されないので、待たせた時間はそれ以下）。

承認待ちの通知は、発生した瞬間に1回出るだけで、見逃すと手掛かりが残らない。動かしっぱなしの作業は、止まっていても静かなので気づけない。

  • 対策として、セッションを起動するたびに「返事を待ったまま止まっている他のセッションが無いか」を点検するコマンド（session-check）を作り、起動時の手順に加えた。何も出なければ正常、出たらそのタブを見に行く
  • この点検には回帰テスト（直したことで別のところが壊れていないかを確かめる自動テスト）を21件付けた
