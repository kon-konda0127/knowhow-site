# なぜ重要か

これを読むと、AIを何本同時に動かすかを、他人の体験談ではなく自分の事故履歴から決められる。

並列数は速度の話に見える。実際に効いてくるのは、同時に動いている作業どうしがぶつかる確率のほうになる。

# 何があったか

  • 個人開発の体感として、MAX5倍プランと並列12ターミナル程度が妥当という共有
  • 構成の内訳も紹介されていた。画面はAI、ストア連携はストアのAPI、画面操作はブラウザ連携、申請と課金は専用サービス、バックエンドはクラウドのデータベース
  • ※個人1人の体験談で、再現性の担保はない。誇大な表現は少なめだった

# うちの体制ではこう使う

2026-08-15、この投稿は見送りと判断した。

取り込むべき具体的な変更がなかったのが直接の理由になる。スマホアプリのストア申請は、今のところ手がけていない領域でもある。

並列数については、うちには参考になる記録がある。同じ時期に最大6つのターミナルを同時に動かしていて（2026-08-14の実測）、12には届かないが、8/13から8/17までの5日間で7件の事故が起きた。

# うちで実際に起きたこと（日付と事実だけ）

  • 8/13: あるAIが自分の変更をGitに記録（コミット）したとき、隣のAIが記録待ちに並べていた25ファイルを巻き込み、26ファイル分の記録になった
  • 8/14: 記録するファイルを「このフォルダの中」と指定したら、隣のAIが作業中だったファイルまで一緒に記録された
  • 8/15: 公開しない前提で記録だけしておいた原稿が、隣のAIが公開の操作（push）をした瞬間に、連なって公開された
  • 8/16: Gitが作業中に置く「使用中」の目印ファイルが消えずに残り、全ターミナルの記録が止まった。10:35と12:15の2回
  • 8/17: 隣のAIが作業中だった同名のファイルを、別のAIが「自分の消し忘れ」と思い込んで削除した（実害なし・復旧済み）
  • 8/17: AI社員のルールや道具を実際に使う場所へコピーする配布スクリプトがフォルダを丸ごと配る作りだったため、他のAIの作業中ファイルまで環境へ入った
  • 8/17: テストを実行しただけで、その配布スクリプトが本番の設定に向かって走ってしまう作りのテストが3セット見つかった（隔離した環境で走る形へ是正）

最後の1件は少し毛色が違う。並列のせいだと思って調べたら、1つのターミナルが自分で自分の環境を書き換えていた。並列の問題だと思っていたら、単独の自爆だった、という裏返しである。

# 台数ではなく、分け方

7件を並べて気づいたのは、どれも「台数が多すぎた」せいではないということ。ぶつかったのは、誰がどのファイルを触るかが決まっていなかった場面ばかりだった。だから対策も、台数を減らすことではなかった。

  • 記録はファイル単位で指定する: フォルダごとではなく、変更した1ファイルずつ名前を挙げて記録する。守れていない操作は、仕組みが機械的に拒否する
  • 先に「誰が何を触るか」を宣言する: 仕事に番号を振り、着手するときに触るファイルの範囲を宣言する。範囲が重なる着手は拒否される
  • 配るものはリストで決める: フォルダ丸ごとではなく、配ってよいファイルだけを列挙して配る

12という数字が合う環境もあるはずだ。うちで確かめられたのは、台数ではなく、この「分け方」のほうが効いた、というところまで。台数を先に決めるのではなく、作業の分け方を先に決める。分け方が決まっていない状態で増やすと、速くなる前に事故が増える（この項は筆者の考察）。

# よくあるミス・落とし穴

以下は筆者の考察。

  • 他人が言った並列数をそのまま自分の環境に持ち込む
  • 増やす前に、作業の分離（どのファイルを誰が触るか）を決めていない
  • 速度の指標としてだけ見て、事故率の指標として見ない
