# なぜ重要か

タスクの重さに応じてAIモデルを使い分けられると、品質を保ったままAI利用コストの構造そのものを変えられる。

全タスクを最上位モデルに任せる使い方は、利用枠がすぐ尽き、費用もかさむ。これはAIコーディング全般に効く考え方で、ツールを入れなくても「振り分けの発想」だけで今日から使える。

# しくみ（なぜ効くか）

  • subagent（サブエージェント）とは、親のAIが作業の一部を子のAIに切り出して並行処理させる仕組み。通常は親も子も同じモデルで動く
  • 子のAIごとに使うモデルを変えられれば、重い判断と軽い繰り返し作業でコストにメリハリをつけられる
  • 振り分けの考え方: 重い判断（設計・レビュー・要件整理）は上位モデル、定型的な繰り返し作業（コード生成・変換）は軽量モデル
  • 効く理由: AI作業の大半は「軽い作業」で、そこに最上位モデルの単価を払う必要がない
  • 判断の質が結果を左右する少数の場面にだけ、高いモデルを集中させる
  • ただしどこで線を引くかを決めるのは人間の仕事。判断が要る仕事まで軽いモデルに振ると、品質のほうが落ちる

# うちの体制ではこう使う

  • この振り分けは、当サイトの開発体制で人力で実践しているものと同じ発想
  • サブエージェント7体には役ごとに使うモデルを固定している（2026年8月時点）。仕様書係はいちばん軽いモデル、テスト役・監査役・校正役・機微判定の4体は標準のモデル、監査役だけは大きな案件で上位モデルへ引き上げる。画面の初版と記事の初版を書く2体は親のモデルを継ぐ
  • 外部のAIも同じ発想で分けている。司令塔（Claude）が設計と検収を握り、読み書き量の多い作業は定額のCodexへ読み取り専用で、Google連携の確認は無料枠のGeminiへ控えめに（体制規約として文書化済み）
  • 同じ考え方の延長で、2026-08-17には記事の初版を書くAIをいつもより軽いモデルで1本走らせる試しもした（結果は移行の記録に1行残してある）
  • ツールを入れなくても、「このタスクは判断が要るか、繰り返しか」で振り分ける習慣だけでコスト効果がある

# 導入を見送った理由（2026-08-16 裏取りの結果）

当初は「ツールでも取り入れる」と書いていたが、実際に調べたところ導入対象そのものを特定できなかったため見送った。理由は3つ。

1. 同じ名前で、まったく無関係なパッケージが実在する

npmには model-router という名前のパッケージが確かに存在する。だが中身は2012-12-21に初版が公開されたサーバー用のルーティングライブラリ（最終更新2024-04-09）で、AIのモデル振り分けとは何の関係もない。リポジトリ欄も未設定だった。

元の紹介手順どおりに「model-routerをインストール」すると、この別物が入る。 悪意のある偽物ではなく、たまたま同じ名前のパッケージが先に登録されていただけだ。それでも、入れれば目的とは違うものが入る。

2. 該当するツールのリポジトリ・作者が特定できない

紹介元の投稿にはリポジトリURLも作者名もなく、GitHubを検索しても該当するツールは見つからなかった。名前が似た汎用のLLMルーターは複数あるが、いずれも別物である。

3. 機能の実体はCodex本体の設定で、現在は標準で使えない可能性が高い

調べた限り、この機能は第三者ツールではなくCodex CLI本体の設定（config.toml の subagent 設定）に関するものだった。公式リポジトリには「サブエージェントごとにモデルを指定できるようにしてほしい」という未解決の要望が複数上がっている。

つまり標準では実現できていない。

さらに、あるバージョン以降はサブエージェントが親の設定を引き継ぐ仕様に変わったという報告もある。

2026-08-17 追記（この節の前提が変わった）: 上の「未解決の要望が複数」は、この記事を書いた8/16の時点で既に古かった。公式リポジトリの要望 Issue #14039「Allow per-subagent model/provider/profile selection」 は 2026-08-05 に completed で close されており、閉じる際に OpenAI 側から「サブエージェントはモデル・推論強度・プロバイダ・役割の設定に対応した」と示されている（エージェント定義ファイルに model を書く形。当方は未検証）。つまりCodex 本体で振り分けができるようになっていた。この変化は「第三者ツール model-router を入れる理由をさらに減らす」方向なので、見送りという結論は変わらない（理由1・2は不変。将来 Codex 側でサブエージェントを使うなら、第三者ツールではなく本体の設定を一次情報で確認する）。原因は、Web検索の要約を根拠にして Issue の状態欄を自分で開かなかったこと。

# それでも損はしなかった

見送りで失ったものは無い。このツールが自動化しようとしていた考え方（重い判断は上位モデル、繰り返し作業は軽いモデル）を、すでに人力の運用ルールとして持っていたからだ。

道具を入れる前に「それで何が良くなるのか」を自分の言葉で言えるなら、道具が無くても価値の大半は先に取れている。

# よくあるミス・落とし穴

  • 名前が一致することを、同じものだと思い込む。 偽物がなりすます場合だけでなく、無関係なパッケージが先に同じ名前で登録されている場合もある。決め手になったのは、作者・リポジトリ欄・初版の公開日
  • 全タスクに同じ最上位モデルを使う（コスト過多になりやすい）
  • 逆に、判断が要るタスクまで軽量モデルに振ると品質が落ちる
  • 振り分け基準を決めるのは人間の仕事（この2項は筆者の考察）
