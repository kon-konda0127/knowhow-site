AIをほぼ使えていなかった私が、有料プランで1週間"ガチって"起きたこと

カテゴリ: コラム > AI活用 公開: 2026-08-12（第1版） 📖 約5分で読めます
#AI活用 #Claude #はじめてのAI #振り返り

8月7日、ClaudeのMAXプラン（月額200ドルの上位サブスクリプション）を契約しました。それまでの私は、正直AIをあまり使えていませんでした。それから約1週間。アプリ4本と公開サイト1つができて、記録に残る失敗が5件ありました。

先に結論を言うと、いちばん効いたのは「AIを賢く使うテクニック」ではなく、最初の1日でAIが安全に働ける仕組みを作ったことだったと考えられます。この記事では、その1週間を「事実」と「考察」に分けて振り返ります。感想文にならないよう、論文の作法（事実と意見を混ぜない）を借りました。

# 背景

  • 筆者はプログラミング初心者。コードはAI（Claude Code）に書いてもらい、自分は指示と判断だけを担当
  • 2026-08-07にMAXプランを契約し、そこから毎日AIと作業
  • この記事の一次資料は、毎日AIに書かせていた作業日報と、失敗だけを分類して記録するミス台帳
  • つまりこれは私1人・約1週間の記録（いわゆるn=1）です。その限界は記事の最後に書きます

# 事実：1週間で起きたこと（時系列）

ここは「起きたこと」だけを書きます。評価や意見は考察のセクションまで我慢します。

  • 8/8: いきなりアプリを作らず、丸1日を「体制づくり」に使った。①全ファイルをGitHubへバックアップ（作業後の自動バックアップ込み）②作業を大中小の規模に分類する基準の制定③作った本人とは別のAI人格にレビューさせる監査ルール④別会社のAIを「社外監査人」として混ぜる規約（daily_report.md 2026-08-08）
  • 8/9: レシピ管理アプリ（自作）へ機能追加。スマホ対応・買い出しリスト・料理履歴など（daily_report.md 2026-08-09）
  • 8/10: 株の指値注文を支援するツールを、仕様書作成→実装→テスト→監査まで1日で完了。このときテスト担当のAIが「対話式の入力が2問目以降を無言で取りこぼす」バグを発見した（daily_report.md 2026-08-10）
  • 8/10: 同ツールに株価データAPIの実キーを入れたところ、HTTP 410エラー。API側が全面刷新（V2移行）されており、仕様書の前提が古かったことが実行して初めて発覚した（daily_report.md 2026-08-10）
  • 8/11: 夜間にAIへ無人で作業させる仕組みを作ったところ、監査で4回の差し戻しを受けた。当初の「危険な言葉（削除・送信など）を検知したら止める」方式が、カタカナ言い換えや英語の同義語で次々にすり抜けられたため。最終的に「あらかじめ許可した種類の操作しか物理的に実行できない」方式へ作り直して合格した（daily_report.md 2026-08-11）
  • 8/11: 公開サイトの画像置き場の設計ミスを実機確認で発見。手元のテストでは表示されるのに、本番の公開範囲設定では画像が全て404になる配置だった（daily_report.md 2026-08-11）
  • 8/12: 失敗を分類して記録する「ミス台帳」を新設。1週間の記録対象の失敗は5件だった（mistake_log.md 2026-08-12時点）
  • 期間合計: 完成したのはアプリ4本（レシピ管理・自炊記録・株の指値支援・買い物の要不要判定）、公開サイト1つ（今読んでいただいているこのサイト）、自動化・安全まわりの仕組み3つ（daily_report.md 2026-08-08〜2026-08-12の各エントリ）

# 分析：失敗5件を分類してみる

事実に現れたパターンを分類します。ここでもまだ「良い/悪い」は言いません。

  • 失敗5件の内訳は「仕様の前提が古い」「ツールの隠れた制約」「本番環境でだけ起きる」「接続設定の相性」「安全設計の穴」が各1件
  • 5件に共通するのは、作る前に前提を検証していれば防げたという点。AIの実装能力そのものの失敗（コードが書けない・バグだらけで動かない）は、この分類では0件だった
  • 「作った本人ではないAI」による監査が、完成・公開前に見つけた問題は少なくとも7件（入力の取りこぼし、計算式の分母の不整合、安全対策のすり抜け複数、など）
  • 安全対策を許可リスト方式へ作り直した後の監査では、42件のテストが全て合格し、追加の敵対的パターン10件でも同じ種類のすり抜けは見つからなかった（daily_report.md 2026-08-11）
  • 初日に作った体制（バックアップ・規模分類・監査ルール）は、その後の6日間の全案件で毎回使われた

# 考察：何がスマートだったのか

ここからは私の解釈です。断定はせず、そう「考えられる」の範囲で書きます。

  • 最初の1日を体制づくりに使ったのは、遠回りに見えて最も効率が良かったと考えられます。特にバックアップの自動化は「失敗しても戻せる」という安心につながり、初心者でも思い切ってAIに任せられるようになりました
  • 「作るAI」と「チェックするAI」を分けるのは、個人の趣味開発でも機能すると言えそうです。会社で経理と監査を分けるのと同じ理屈で、作った本人（AI）の自己申告だけでは7件の問題は出てこなかった可能性があります
  • 失敗の分類から見ると、AIに足りないのは能力よりも「前提が今も正しいかの確認」だと考えられます。「そのやり方、今も有効？最新の公式情報を確認した？」と一言聞くだけで、5件のうち何件かは防げたはずです
  • 安全対策は「危険を検知して止める」より「そもそもできることを許可リストで絞る」方が堅牢だと考えられます。言葉の検知は言い換えとのいたちごっこになりましたが、許可リスト方式への変更後は監査でも同じ種類のすり抜けが見つかっていません（分析セクション参照）。これはAIに限らず応用が利く考え方だと思われます
  • 逆に、もっとスマートにできたこともあります。外部サービスとつなぐ作業は、作り込む前に「最小の接続テスト」を最初の30分でやるべきだったと考えられます。API刷新の発覚が実キー投入時までずれ込んだのは、この順序を踏まなかったためです

# この記事の限界

  • 記録者は私1人、期間は約1週間です（n=1）。別の人・別の期間で同じ結果になる保証はありません
  • 一次資料の日報は「私とAIが」書いたものなので、うまくいった作業ほど詳しく書かれる偏り（生存者バイアス）があり得ます
  • 上位プランという課金環境の恩恵（上位モデル・利用量の余裕）と、体制づくりの効果を厳密には分離できていません

# まとめ：これから始める人が今日からできること

  • 最初にバックアップ体制を作る（AIに「Gitでバックアップ体制を作って」と頼むだけでよい）
  • AIの提案には「その前提、最新？」と1回聞く。外部サービスがからむなら特に
  • 失敗したら、AIの能力のせいにする前に「どの前提が崩れたか」をメモする（私はこれを台帳にしています）
  • AIに自動で何かをさせたくなったら、禁止リストではなく許可リストで考える
  • 外部サービスとの連携は、作り込む前に30分の接続テストから始める

n=2以降（2週目以降の私）でこの考察がどう変わるかは、また続編で書くつもりです。
