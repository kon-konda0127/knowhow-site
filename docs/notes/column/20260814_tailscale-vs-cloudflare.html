自宅のWi-Fi内でしか使えないアプリを、外出先からも開けるようにしたい。よくある要望だと思う。

方法はいくつかある。今回はそのうち2つを実際に手を動かして試し、片方から片方へ乗り換えることになった。

この記事は、その乗り換えの理由と、乗り換えた先で見つかった「気づいていなかった穴」の記録。

背景#

自宅のWi-Fi内でしか使えないアプリ（レシピ管理・使用状況の確認画面など、非機微なもの数本）を、外出先のモバイル回線からも開けるようにしたい。これが今回の出発点でした。

自宅サーバーを外から触れるようにする方法はいくつかあります。有名どころだけでも、自分専用のプライベートなネットワークを作る方式（Tailscale）、クラウド事業者の仲介で公開する方式（Cloudflare Tunnel）、自分でVPNサーバーを立てる方式（自前WireGuard）の3つが候補に挙がりました。この記事は、そのうち2つを実際に手を動かして試した記録です。

事実：何が起きたか#

ここは「起きたこと」だけを書きます。評価は次の章から。

事前3方式を比較検討し、いったん保留
詳しく

コスト・難易度・セキュリティ・アプリ側の変更要否で3方式を比較し、設定の単純さを理由にTailscaleを推奨案としてまとめた。ただしこの時点では実装に着手せず保留にしていた。

出典: 仕様書ドラフト（2026-08-10）

8/14Cloudflare Tunnelで着手
詳しく

改めて要望を受け、仕様書を作成。固定のURL・きれいなドメイン名・メール認証（ワンタイムPIN）という設計で承認を得て、必要なプログラム（cloudflared）のインストールまで完了させた。

出典: 作業日報 2026-08-14

8/14「無料でできない？」で方式転換
詳しく

調べ直すと、Cloudflare Tunnelで固定URLを使うには独自ドメインの取得が必須（年1,000〜2,000円程度）だと分かった。一方、比較検討段階で候補に挙がっていたTailscaleは、個人利用なら6ユーザー・台数無制限まで完全無料（無料枠が数ヶ月前に拡大されていた）。ドメイン代の要否という一点で、方式を丸ごと切り替えることにした。

出典: 作業日報 2026-08-14

8/14実装：どのアプリを外に出すか仕分け
詳しく

外に出してよいアプリと出してはいけないアプリを、「個人情報や家計データなど機微な内容を扱っていないか」を基準に仕分けた。機微なアプリは、そもそも自分のパソコン以外からは開けない設定になっていることを実際に確認し、対象から外した。

アプリの入口となる画面には、「自宅Wi-Fi内から開いた時」と「外出先から開いた時」を自動判定し、外出先では対象アプリだけにリンクを出す仕組みを実装した。

出典: 作業日報 2026-08-14

8/14外部AI監査で重大な指摘
詳しく

別系統のAI（Codex）にコードのレビューを依頼したところ、「対象外アプリを『リンクを表示しない』だけで除外しており、ネットワークへの到達自体は防げていない」という指摘が入った。該当アプリは全アドレスで待ち受けているため、URLを直接指定すればアクセスできてしまう状態だった。

加えて、「自宅Wi-Fiかどうか」の判定ロジックの穴、リンクの行き先を検証せずそのまま使っている点も指摘された（指摘は計5件、うち重大1件）。

出典: Codex社外監査 2026-08-14

8/14ネットワーク側でも塞ぐ
詳しく

Tailscale自体が持つアクセス制御機能（ACL）を使い、「スマホからパソコンへは、許可した入口だけを通す」というルールを追加。リンク表示（画面上の防御）とアクセス制御（ネットワーク上の防御）の二重構成にした。判定ロジックも、判定に迷うホスト名はすべて「外出先」として安全側に倒すよう書き換えた。

修正後、テスト担当のAIが43件のテストを再実行して合格、最終監査担当のAIが独自に34件のテストを追加実行して合格。スマホのWi-Fiを切った状態で、許可アプリは開けること・対象外アプリには繋がらないことを実機で確認した。

出典: 作業日報 2026-08-14

分析：何が起きていたのか#

出来事を整理すると、2種類の「見落とし」に分けられます。

  • コストの見落とし：固定URLにはドメイン代が要る、を導入直前まで確認していなかった。気づいたきっかけは「無料でできない？」という素朴な問い直し
  • セキュリティ設計の見落とし：「リンクを隠す」＝「到達できなくする」だと思い込んでいた。気づいたきっかけは別系統AIによる第三者監査

どちらも、最初の設計段階では気づきませんでした。共通しているのは、当事者だけでは見えない前提が入り込んでいたという点です。コストの見落としは「ざっくり無料だと思っていた」思い込み、セキュリティの見落としは「画面から消せば安全」という思い込み。どちらも、外から一言問い直されて初めて崩れました。

考察：何を持ち帰れるか#

  1. 「無料か」を最初に聞く
    方式の比較検討はしていたのに、実装が進んでから「無料でできないか」と聞き直す形になりました。コスト条件を比較表を作る前に確認しておけば、この手戻りは防げたはずです。
  2. 「隠す」と「塞ぐ」は別レイヤーの話だと意識する
    画面上の防御（表示制御）とネットワーク上の防御（アクセス制御）は独立しています。片方だけでは「見えないけど繋がる」状態が普通に起こります。
  3. 第三者にレビューさせる価値は、思い込みの検出にある
    自分（や実装を担当したAI）は「隠したから安全」という前提の中でしか考えられません。その前提を疑えるのは、前提を共有していない第三者だけです。
  4. 無料枠は定期的に見直す価値がある
    今回使ったTailscaleの無料枠は、調べた時点で数ヶ月前に拡大されたばかりでした。「昔調べた時は微妙だった」選択肢が、今は変わっているかもしれません。

使い分けの整理（比較表）#

今回検討した3方式を、実際に手を動かした範囲でまとめます。

Tailscale（今回採用）

  • 費用：無料
  • 難易度：やさしい（両端末にアプリを入れてログインするだけ）
  • 見た目のURL：機械的な文字列（例：端末名.tailnet名.ts.net）
  • 向いているケース：個人・少人数で、費用をかけずに自分の端末だけがアクセスできればよい場合

Cloudflare Tunnel

  • 費用：ドメイン代（年1,000〜2,000円程度）＋無料枠
  • 難易度：やや複雑（ドメイン取得・認証設定が必要）
  • 見た目のURL：好きな文字列にできる（例：myapp.じぶんのドメイン）
  • 向いているケース：きれいなURLが欲しい・スマホ側に専用アプリを入れたくない場合

自前VPN（WireGuard等）

  • 費用：無料
  • 難易度：難しい（ルーターの設定変更・サーバー構築が必要）
  • 見た目のURL：機械的な文字列
  • 向いているケース：外部サービスに一切依存したくない・技術的な自由度を最優先する場合

3つとも「外部にサーバーを公開しない」という土台は共通しています。違うのは、その手前に何を挟むか（専用ネットワークか、クラウド事業者の仲介か、自前の暗号化トンネルか）と、それに何を払うか（時間か、お金か、運用の手間か）。今回は「スマホ側にアプリを入れる一手間」を払って、お金と設定の複雑さを節約した形になります。

この記事の限界#

  • 筆者1人・1プロジェクトの記録です。組織の規模や、扱うアプリの性質が変われば、最適な選択も変わってくるはずです
  • 自前VPN（WireGuard）は実際には構築していません。表の難易度評価は、仕様検討時に調べた情報をもとにしています
  • 無料枠の条件（ユーザー数・台数上限）は提供事業者の都合で変わります。この記事の数字は執筆時点のものです
  • セキュリティ監査は今回1回・1つのAIツールによるもの。指摘の5件で全部だとは思っていません

まとめ：今日からできる3つ#

  1. 外部アクセスの方式を選ぶ前に、「無料でできる選択肢はどれか」を最初に確認する
  2. 「画面から消した」「リンクを外した」という対策は、ネットワーク的にも到達できなくなっているかを必ず別途確認する
  3. 「隠したから安全」で終わらせず、隠したはずの入り口へ直接アクセスを試す（自分でダメなら、他人や別のAIに試させる）
