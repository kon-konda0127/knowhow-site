# なぜ重要か

これを読むと、「AIの回答が長い」問題に設定で効く手があるかもしれないと分かる。

そして、自分たちが今まで減らしてきたのがどちらの読む量だったかを区別できるようになる。

# しくみ（なぜ効くか）

  • 出力の型をあらかじめ指定しておくと、毎回同じ形で返ってくる
  • 短く答えるモードは、結論を先に置き、説明を省く。足りなければ後から掘る前提の設計になっている
  • 効くのは「毎回同じ指定を書かなくてよくなる」点。都度お願いすると、忘れた回だけ長くなる
  • 切り替えは設定の1行、または画面から選ぶだけとされていた

# うちの体制ではこう使う

実測1: 機能は実在し、うちは使っていない

実行ファイルに該当する文字列があることを確認した。確認方法そのものが一度壊れていたので、既にある機能の名前でも同じ検索を試し、ちゃんと見つかることを先に確かめてある。

設定ファイルを開くと、この項目は未設定だった。既定のまま使っている。

実測2: 減らしてきた「読む量」が違う

うちは今月、AIが起動時に毎回読む規程を13本から5本へ減らした。読み込みの量が減れば、その分だけ考える余地が増えるという理屈である。

今回の機能が減らすのは、そこではない。減るのは人が受け取る文章の量で、AIの読み込みは変わらない。

同じ「読む量を減らす」でも、減る側が違う。両方やる意味はあるが、片方をやったから片方も済んでいる、とはならない。

実測3: 短くすると落ちるものがある

うちの報告は、実行した結果をそのまま貼る書き方を規程にしている。テストの出力、終了コード、件数。要約する時は「抜粋」と明記する決まりまである。

理由は、過去に数字を手で書いて間違えたことが何度もあったからで、貼れば間違えないという発想である。

短く答えるモードが、この「そのまま貼る」とどう噛み合うかは分からない。結論だけ先に出して根拠を省く形になると、規程が求めているものが落ちる。

そこも含めて、入れてから数回見ないと判断できない。

実測4: だから判定は未判定にした

  • 機能は実在する ＝ 確認できた
  • うちは未設定 ＝ 確認できた
  • 入れると良くなるか ＝ 未検証
  • 設定の切り替えは環境の変更なので、こちらの判断だけでは入れられない

「良さそう」で入れないのがうちの決まりなので、未判定として置く。

# よくあるミス・落とし穴

  • 「読む量を減らす」を一括りにしない。AIが読む量と、人が読む量は別のつまみである。片方を減らしても、もう片方は変わらない
  • 短くなって落ちるものを先に考える。根拠や実行結果を省く形になると、間違いを見つける手がかりごと消える
  • 設定は「入れてみた」で終わらせない。入れた後に、判断材料が落ちていないかを数回見る。それをやらないなら入れないほうがいい
  • 確かめ方が壊れていないか、先に確かめる。今回も答えが分かっている対象で同じ手順を試し、それが正しく見つかることを確認してから結論を書いた
