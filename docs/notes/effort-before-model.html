# なぜ重要か

これを読むと、AIの費用を下げたい時にモデル以外の調整つまみがあることが分かる。

そして、自分がそのつまみを既にどこに置いているかを、議論の前に確認できるようになる。

# しくみ（なぜ効くか）

  • 同じモデルでも、どれだけ考えさせるかを段階で指定できる。浅いほど速く安く、深いほど遅く高い
  • 「思ったより答えが浅い」時、原因はモデルの能力ではなく深さの指定が低いことかもしれない
  • モデルを上げるのはいちばん大きく効くが、いちばん高い手段なので、先に安い調整を試す順番になる
  • 投稿はもう1つ挙げていた。設計は上位モデル、実行は下位モデルへ自動で切り替えるやり方で、費用は下位モデル並みに収まるとしていた

# うちの体制ではこう使う

実測1: 深さは既に上から2番目で固定していた

設定ファイルを開いた。

effortLevel: 'xhigh'

5段階のうち上から2番目である。意識して選んだ記憶は、この記事を書いている時点では辿れなかった。

そしてうちの記録を検索すると、深さの話はほとんど出てこない。出てくるのはモデルの話ばかりで、どのモデルをどの作業に割り当てるか、上位モデルをいつ使うか、といった議論が何日も続いていた。

つまみは既に上げてあったのに、誰もそのつまみの話をしていなかった。

実測2: もう1つの提案は、検討して採らないと決めていた

「設計は上位、実行は下位へ自動で切り替える」やり方について、うちの費用の検討資料にこう書いてあった。

> プランモードに出入りするたびモデルが切り替わるため、そのたびキャッシュが飛ぶ

読み込みの内容は一定時間だけ再利用が効くが、モデルが変わると作り直しになる。切り替えの回数が多いほど、安いモデルを使っても読み込みのコストを何度も払う。

同じ機能でも、費用が下がる人と上がる人がいる。行ったり来たりの多い使い方では、上がる側に回る。

実測3: 副産物として、記録と実物の食い違いが見つかった

同じ検討資料に、うちの設定がこう書いてあった。

> model: "opus"・effortLevel: "xhigh" が固定済み

深さは合っていたが、モデルが合っていなかった。実際の設定は別の値になっていた。さらに設定の変更履歴を見ると、現在の値になった経緯が記録されていない。

検証のつもりで自分の設定を開いたら、記録のほうがずれていた。これは本日6件目の同じ型で、別に直すことにした。

# よくあるミス・落とし穴

  • モデルの話をする前に、自分の設定を開く。うちは何日もモデルの割り当てを議論していたが、深さのつまみが既にどこにあるかを誰も見ていなかった
  • 「安くなる」を鵜呑みにしない。切り替えが多い使い方では、読み込みの作り直しでかえって高くつく場合がある。効くかどうかは使い方で変わる
  • 設定の記録は、実物とずれる。記録を根拠に判断する前に、実物を開いて突き合わせる。今回はそれで食い違いが見つかった
  • 「意識して選んだ記憶が無い」を、そのまま書く。辿れなかったことを辿れたように書かない
