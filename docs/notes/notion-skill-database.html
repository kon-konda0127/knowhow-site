# なぜ重要か

これを読むと、便利そうな管理ツールを前にして「置き場所を増やすべきか」を先に判断できる。

管理表は増やした時点では気持ちがいい。困るのは、同じ情報が二か所にあると気づいた後になってからになる。

# しくみ（なぜ効くか）

  • Notionのデータベース（表形式のページ）を、右クリックの「スキルに変換」でスキルを管理するデータベースへ変換する機能
  • 表の列として、スキル名・カテゴリ・ステータス・説明・関連エージェントが並ぶ
  • 狙いは、作ったスキルを一覧で見渡し、使い回せる状態にすること
  • ※このノートは投稿の画面写真からの要約。機能が実在することは手元のNotion連携に同種のツールがあったので確認できたが、変換の実際の動作は未検証

# うちの体制ではこう使う

2026-08-15、この投稿は見送りと判断した。

理由は、スキルの正本が手元のフォルダにあり、Notionを普段の作業で使っていないため。導入すると、同じスキルの情報が手元とNotionの二か所に並ぶ。

前日にも同じ形の判断をしている。手順をどこに固定するかという別の案件で、「すでに規約のファイル側で固定しているなら、二重に持つ意味がない」という基準を立てたばかりだった。

  • 当時のスキルは10件（2026-08-17に数え直したら12件）で、探すのに困っていない。一覧表を作る動機が今はない
  • 代替案として記録したこと: 将来スキルが増えて探せなくなったら、道具を増やさず、すでに使っているノートアプリ（Obsidian）側で、手元のフォルダを表として眺めるだけの一覧（Bases）を作る
  • 見るだけの一覧なら、正本は手元のフォルダのまま動かない。二重管理にはならない（この項は筆者の考察）

# 置き場所が2つあると何が起きるか（2026-08-17の実話）

見送りから2日後、まさにその「2か所」で起きた出来事がある。当チームはスキルを「Gitで管理する置き場」と「AIが実際に読む置き場」の2か所に置き、前者から後者へ配る仕組みにしている。

この日、デザインの決まりを書いた規範スキルの改訂版（v2.10）が、AIが読む側には入っているのに、Gitの記録にも監査役のレビュー記録にも無いことが分かった。実際に読まれている版と、記録に残っている版が、別物だった。

そこで中身を精査して追認する作業に入り、直すべき点が4件見つかった。その途中で今度は、学習台帳（学んだことを記録する一覧）の記述とスキル本体の文章が食い違った。当初は「台帳が正しく、スキル本体が誤り」と見てスキル本体を直しかけたが、念のため実物のアプリの設定を照合すると逆だった。

  • 数値の書体: 台帳は「明朝」と記録。実物は等幅（数字の幅がそろう書体）
  • 数値の文字サイズ: 台帳は20px。実物は27px。しかもこの誤りはスキル本体の2か所にそのまま写されていた

台帳のほうが二重に誤っていた。台帳を信じて直していたら、正しいものを壊すところだった。是正して v2.11 とし、監査役の承認を得てコミットした。

置き場所が増えると、どちらが正しいかを毎回確かめる仕事が増える。しかも、確かめずに直すと正しいほうを壊す。台帳は記録した時点の記憶で、実物は今そこにあるもの。食い違ったら、実物を見に行くしかない（この項は筆者の考察）。

# よくあるミス・落とし穴

以下は筆者の考察。

  • 一覧が欲しいだけなのに、管理する場所ごと増やしてしまう
  • 正本をどちらにするか決めないまま両方に書き、後からどちらが新しいか分からなくなる
  • 10件で困っていない段階で、100件向けの仕組みを入れる
