【見送り】サブエージェントの並列コスト対策は、うちでは重複だった

⏱ 30秒でわかるこのノート
  • AIの子分（サブエージェント）を設定なしで並列に走らせると、利用量が一気に膨らむ
  • 対策は3つ。モデルの使い分け・推論強度の設計・設定ファイルの整備
  • 並列数を増やすことは最適化ではない。1体あたりの仕事量を絞る方が効く
  • 自分の体制では見送り。時間の目安・停止条件・振り分けはすでに規程にあったため

# なぜ重要か

これを読むと、並列実行で利用枠が急に減る事故を避けられる。

サブエージェントは速い。ただし同時に走った分だけ消費する。速さの対価が見えないまま増やすと、気づいた時には枠が尽きている。

# しくみ（なぜ効くか）

  • サブエージェントとは、親のAIが作業の一部を子のAIに切り出す仕組み。並列に走らせると、同時進行する分だけトークン（AIの利用量の単位）を消費する
  • 元の投稿が挙げていた対策は3点。①モデルの使い分け ②推論強度（effort）の設計 ③エージェント設定ファイルの整備
  • 推論強度とは「どれだけ念入りに考えさせるか」の設定。すべて最大にすると、軽い作業にも重い費用がかかる
  • 同じ発想の続きとして、Codex subagent のモデルルーティングも参照

# うちの体制ではこう使う

当チームの監査担当（テスト役・最終監査役）は、まさにサブエージェントとして動いている。起動の作法は規程にすでに書いてある。

  • 依頼文に作業時間の目安を書く（軽いレビューなら15分、全面審査なら30分）
  • 長引きそうな依頼はバックグラウンドで走らせ、目安の2倍を過ぎたら一度だけ状況を確認し、それでも応答がなければ打ち切って範囲を絞り直す
  • 読む量が多く出力が長い作業は外部の定額AIへ逃がし、判断と統合は司令塔の手元に残す

2026-08-14にこの投稿を検討し、見送りと判断した。上記がすでに明文化されており、新たに足すものが無かったため。

残った視点（この項は筆者の考察）: 起動する前に「時間・範囲・停止条件」を決める。並列数そのものより、1体に渡す仕事の量を絞る方が効く。

# よくあるミス・落とし穴

以下は筆者の考察。

  • 並列数を増やすこと自体を最適化だと思ってしまう
  • すべての子分を最上位モデル・最大の推論強度で走らせる
  • 停止条件を決めないまま起動し、終わらない相手を待ち続ける
