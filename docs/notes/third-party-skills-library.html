# なぜ重要か

これを読むと、他人のスキル一式を受け取る前に何を見るべきかが分かる。

配布物は「良さそうか」ではなく「中で何が動くか」で判断する。紹介文と実物は別のものである。

# しくみ（なぜ効くか）

投稿の骨子はこうだった（要約）。

  • 個別のプロンプトを溜めるのをやめ、繰り返し使う型をスキルにする
  • 型は3つで足りる: 手順を尋ねる型／自分の人物像を渡す型／スキル自体を作る型
  • 入力は音声のほうが速く、質問に答えさせると曖昧さが残らない
  • 設定は増やさず、スキルと文脈の2つだけにする

上3つの発想は正しいと思う。うちも同じ方向に動いてきた——手順を固定するスキル、判断基準を書いた規程、それらを作る手順書がある。

# うちの体制ではこう使う

実測1: 「3つの型」は既にある

投稿の型うちで対応するもの
手順を尋ねる型作業ごとのスキル（入稿・監査・技術選定など）
自分の人物像を渡す型常時読ませる規程（前提・話し方・判断の基準）
スキルを作る型他のAIの成果物から作法を抽出して規範化する手順書

発想としては既に採っている。新しく入れるものは無い。

実測2: 配布物の受け取り方が、過去に踏みかけた経路と同じ

投稿は「登録すれば一式を落とせる」と案内している。中身を見る前に手元へ置く流れである。

うちは2026-08-15に、これで事故りかけた。急上昇していた第三者のスキルを「作業と噛み合う」として推薦したが、社長が導入ではなく中身の下見を指示し、コードを読んだところ暗号資産ウォレットの認証情報を盗み出すものだった。

その時に決めた確認は3点である。

1. 同名の複製ではないか（作者・作成日・fork有無・星の数を本家と比べる）

2. エントリから辿って、外部への送信と外部プロセスの起動を全部見る。フォルダ単位で網羅する

3. 導入時に走る仕掛けが無いか

この3点を通していない配布物は、良さそうでも置かない。今回の一式も通していないので、置かない。

実測3: 「設定を全部オフ」はうちでは成立しない

うちは常時読ませる規程5本・スキル23本・フック4種で回している。フックは、承認待ちの通知、コミット範囲の機械拒否、作業終了時の記録といった事故を止める側に効いている。

全部オフにすると、止まらなくなるのは作業ではなく事故のほうである。

ただし投稿の言い分も分かる。設定が増えるほど、読まれないまま積み上がる。うちも今日、常時読ませる規程を13本から5本へ減らしたばかりで、そこは同じ問題意識である。減らす方向は正しく、ゼロにするのが行き過ぎという読み方をしている。

# よくあるミス・落とし穴

  • 「良さそう」で配布物を置かない。星の数・紹介文・作者の自己申告は根拠にならない。うちが踏みかけた件では、安全性を説明した文書自体が嘘だった
  • 登録の見返りに配られるものほど、中身を見る手間を飛ばしたくなる。飛ばした先で何が動くかは、飛ばした人には見えない
  • 「設定を全部オフ」を、事故を止める仕掛けごとオフにする意味で受け取らない。減らすべきは読まれない設定であって、止める仕掛けではない
  • 発想と配布物を分けて判断する。今回は発想（3つの型）は採れるが、配布物は採らない、という分け方になった
