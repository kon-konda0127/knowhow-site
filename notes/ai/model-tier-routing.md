## なぜ重要か

これを読むと、「上位モデルを減らせるか」を**意見ではなく自分の記録で**判定できるようになる。

上位モデルを減らす話は、他人の環境の結論をそのまま持ち込んでも当たらない。契約しているものが違えば、選べる配置が違うからである。

## しくみ（なぜ効くか）

投稿の骨子はこうだった（要約）。

- いちばん抽象度の高い層と、その次の設計の層と、検証の層と、実作業の層を**分ける**
- 分けたうえで、層ごとに**要求される能力に見合ったモデルを割り当てる**
- 実作業は GPT-5.6 の3ティア（Sol / Terra / Luna）に任せ、上位モデルの契約は減らす

効く理屈は分かる。層によって必要な能力は違うので、全部を最上位でやるのは払いすぎになる。**この考え方そのものは、うちでも2026-08-14に別の投稿から取り込み済み**である（→「Codexのsubagentごとにモデルを振り分ける」のノート）。

**今回新しいのは「だから上位モデルの契約を減らす」という結論のほう**で、そこが検証の対象になる。

## うちの体制ではこう使う

### 実測1: 契約があるのは4層のうち1層だけだった

投稿の振り分け表を、うちの手元で追えるか確かめた。

| 投稿の層 | 割り当て | うちで使えるか（2026-08-20 実測） |
|---|---|---|
| 抽象 | GPT Pro | **経路なし** |
| 設計 | GPT の高推論 / 上位モデル | 上位モデルのみ |
| 検証 | 上位モデル | あり |
| 実作業 | Sol / Terra / Luna・稀に Grok | **Luna のみ**。Sol・Terra は選択されていない。Grok は**コマンド自体が無い** |

**4層のうち3層は経路が無い。**振り分け表としては採れない。

### 実測2: 最下位ティアを、実作業ではなく検証に置いていた

外部レビュー用のCLIの設定を開いたら、こうなっていた。

```toml
model = "gpt-5.6-luna"
model_reasoning_effort = "xhigh"
```

**GPT-5.6 の最下位ティアに、推論の深さだけ最大を指定して使っていた。**しかも用途は投稿が言う「実作業」ではなく、**社外監査**（自分たちの成果物を外から点検してもらう役）である。

意識して選んだ配置ではなかった。**投稿を検証しようとして初めて、自分の設定を読んだ。**

### 実測3: その最下位ティアが、内部の2者が見逃した欠陥を見つけていた

いちばん重かったのは 2026-08-15 の件である。

書き込み範囲の受け入れ基準として `git check-ignore` を使った負のテストを作り、品質をチェックする役のモデルも「合格」と報告した。ところがこのコマンドは、**追跡済みのファイルに対しては設定がどう壊れていても「該当なし」を返す**。つまり**永久に合格し続ける、中身の無い検査**だった。

**実装を担当したモデルも、品質をチェックする役のモデルも見抜けず、社外監査で初めて発覚した。**

ほかにも、測定の設計そのものを作り直させる指摘（成功率は簡単な仕事を寄せれば上がる、という指摘）や、テスト結果をパイプでつなぐと失敗が握り潰される、という指摘が出ている。**いずれも最下位ティアからの指摘**である。

### 実測4: ただし、その指摘をそのまま実装して2回壊した

同じ記録には逆の例も残っている。

- 「モバイルで図の文字が読めない」という指摘を受けて最小幅を足したら、**記事の本文が画面外にはみ出した**（320px幅で21要素中20要素）
- 「見出しと実データが合っていない」という指摘を受けて補足を書いたら、**その補足自体が事実と違っていた**

**指摘が当たっていることと、指摘どおりに直して良いことは別である。**

### 実測5: 「型があれば下位モデルでできる」は、まだ確かめきれていない

2026-08-18 に、うちの記事執筆に使う Claude の上位モデル（Opus）と下位モデル（Sonnet）で、実績を同じ物差しで測る比較実験を組んだ（ここまでの GPT-5.6 の層の話とは別の計測である）。ただし実際に並んだのは、下位側が note 記事の初版1本、上位側が記事の書き換え5本で、題材も検収者も違う。それぞれの実績はこうだった。

- **下位（Sonnet・1本）**: 校正の重大な指摘0件・軽微1件、検収で手を入れた箇所21か所、依頼文に無い数字0件
- **上位（Opus・5本）**: 校正の重大な指摘0件（5本とも）・軽微3件、検収で手を入れた箇所は計7か所、事実の誤り0件（17項目を数え直して全一致）

**この2行を並べて優劣は言えない。**本数が1本と5本で違い、題材も検収者も違う。うちの記録にも「**この2行の比較から断定しないこと。書けるのは各行の実績まで**」という但し書きが残っている。

書けるのはここまでで、**「型があれば下位モデルでも足りる」は、まだ確かめられていない。**事実の照合が重い題材では、そもそも測っていない。

## 投稿と逆になった点

投稿は**検証を上位モデルに**置き、実作業を下位ティアに置いていた。うちは**検証に最下位ティアを置いて**成果が出ている。

理由は推測だが、外から点検する役に必要なのは**深い推論よりも「文脈を持っていないこと」**なのだと思う。自分で作った人は、自分の思い込みごと点検してしまう。**別系統のモデルであること自体が効いている**可能性がある。

これは**まだ確かめていない**。同じ役を上位モデルにやらせて比べれば分かるが、今回はそこまでやっていない。

## よくあるミス・落とし穴

- **他人の振り分け表を、契約を確かめずに真似しない。**今回は4層のうち3層に経路が無かった。表として採れるかは、意見ではなくコマンドの有無と設定ファイルで決まる
- **「上位が不要」という結論だけを持ち帰らない。**投稿には測定値が無い。持ち帰るなら、自分の記録のどこがそれを支持し、どこが支持しないかまで見る
- **モデルの名前を、知らないまま書かない。**今回 Sol / Terra / Luna は調べるまで何か分からなかった。**知らない名前を推測で説明すると、記事全体の信用が落ちる**
- **外部レビューの指摘を、そのまま実装しない。**当たっている指摘でも、直し方まで正しいとは限らない。うちでは2回、直した結果が新しい不具合になっている
- **自分の設定を読まずに「うちはこうしている」と書かない。**今回いちばんの発見は、**自分たちが既に最下位ティアを使っていたと気づいていなかった**ことだった
